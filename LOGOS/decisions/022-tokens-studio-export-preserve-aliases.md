## Context

Having a `ResolverDocument` + per-set `TokenFile` objects (from ADR-021), the question
is how to serialise them back to a Tokens Studio JSON file that Penpot can import.

Two paths exist:

**Resolve-then-export**: call `Resolver.resolve` first, then emit the merged token set.
All aliases become concrete values. One file per context combination needed for
multi-theme output.

**Preserve-aliases**: export the per-set token trees before resolution. Alias chains
stay as `{dot.path}` strings. Penpot (and Tokens Studio) resolve them at runtime.

## Decision

**Preserve-aliases is the primary and only export path.**

Rationale:
1. The entire purpose of the resolver/modifier system is runtime context selection.
   Exporting resolved values collapses that into a static snapshot, requiring N exports
   for N theme combinations.
2. The resolve-then-export use case (emit concrete CSS for a specific context) is already
   fully covered by `CssEmitter.emitThemed`. No second implementation needed.
3. Penpot natively resolves aliases when applying tokens to shapes, so alias chains are
   not just preserved — they are the *correct* form for the import target.

**Color conversion:**

DTCG color tokens carry structured values (`{ colorSpace, components }`). Penpot's import
accepts only hex strings.

- sRGB colors → `"#rrggbb"` hex. Lossless (sRGB is the design-tool native space).
- Wide-gamut (oklch, p3, lab, …) → nearest sRGB hex approximation, **and** the original
  DTCG value string is written to `$description`:
  `"source: oklch(70% 0.2 120) — converted to sRGB hex for Tokens Studio compatibility"`.
  If a `$description` was already present, the conversion note is appended.
- If a color has an explicit `Hex` fallback (from ADR-016), that hex is used directly
  (no approximation needed, not lossy).

The `$description` field is spec-compliant (DTCG §4.1), round-trips through Tokens Studio
and Penpot, and is surfaced in the Penpot token inspector. It is the appropriate carrier
for any metadata that cannot be represented in the target format's value field.

**Type names:**

DTCG type names are emitted as-is (`"color"`, `"dimension"`, `"number"`, etc.). Penpot
2.14+ accepts DTCG type names directly. No reverse-mapping to Tokens Studio legacy names
(`"fontSizes"`, `"spacing"`, etc.) is performed.

**Public API:**

```fsharp
// In Api module:
exportTokensStudio
    : ResolverDocument
    -> Map<string, TokenFile>
    -> string    // Tokens Studio JSON, ready for Penpot import
```

## Consequences

- Authors can write spec-compliant DTCG tokens, validate with any DTCG validator, then
  call `exportTokensStudio` to produce a Penpot-importable file.
- Wide-gamut colors produce a warning in the return type and a `$description` annotation
  in the output — no silent data loss.
- The exported file will pass the Anima Design Token Validator with zero errors (the
  `$themes`/`$metadata` keys it currently reports are generated by the exporter in
  spec-equivalent form; the token content uses DTCG-valid values).
- Composite token field names (`fontFamily`, `fontSize`, `fontWeight`, etc.) use DTCG
  names in the output, not the Tokens Studio legacy names. Penpot accepts both.
