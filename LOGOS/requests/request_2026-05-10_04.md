`FnTools.DesignTokens` — resolver-document workflows require `tsMathExpression` evaluation integrated into `resolveAll`, not as a post-step

**Context**

The 0.9.0 release of `evaluateMathExtensionsInFile` fixes alias propagation for single-file DTCG workflows (`Format.parse` → `evaluateMathExtensionsInFile` → `flattenResolved`). It does not fix resolver-document workflows.

**Reproduction**

```fsharp
#r "nuget: FnTools.DesignTokens, 0.9.0"
open FnTools.DesignTokens

let resolverDoc = Api.Primitives.parseResolver sotJson |> Result.get
let input = Map ["Breakpoint", "Desktop"; "Density", "Comfortable"; ...]

match Api.Primitives.resolveAll (fun _ -> Error "") input resolverDoc with
| Ok file ->
    let r = Api.evaluateMathExtensionsInFile file
    // r has no warnings
    match Api.Primitives.flattenResolved r.File with
    | Ok tokens ->
        // scale.x1  = ResolvedNumber 20.0   ✓ correct
        // spacing.x1 = ResolvedNumber 16.0  ✗ still stale
```

**Root cause**

`resolveAll` processes a resolver document by merging axis sets and following all `$value` alias references in a single pass. When it encounters `spacing.x1.$value = "{scale.x1}"`, it follows the reference immediately and stores `ResolvedNumber 16.0` (the stale value) as `spacing.x1`'s value. The alias chain is fully consumed — no reference string survives into the returned `TokenFile`.

When `evaluateMathExtensionsInFile` subsequently processes that `TokenFile`, `spacing.x1` is already a concrete `ResolvedNumber 16.0`. There is no alias relationship to traverse. The function correctly updates `scale.x1` to `ResolvedNumber 20.0`, but nothing propagates to `spacing.x1` because the connection no longer exists.

This is a structural incompatibility: the 0.9.0 fix requires alias references to be present in the `TokenFile` at evaluation time, but `resolveAll` eliminates them as part of its contract.

**Requested fix**

`resolveAll` should evaluate `tsMathExpression` extensions on any token that has them, using the merged (but not yet alias-resolved) token context, before following alias references for dependent tokens.

The minimal correct execution order within `resolveAll` for a resolver-document input:

1. Merge all active axis sets into a single token map (values still as raw `$value` — numbers, strings, alias references)
2. **Evaluate `tsMathExpression` for formula tokens, using the merged raw values to resolve `{variable}` references** — `{multiplier}` looks up the already-merged `multiplier` value (1.25 from Desktop axis, having overridden the 1.0 from Foundations/Base)
3. Update formula token `$value` entries in the merged map with evaluated results
4. Follow alias references for all remaining tokens — `spacing.x1 → {scale.x1}` now finds `20.0`, not `16.0`
5. Produce the `TokenFile`

**What is NOT acceptable**

A post-`resolveAll` propagation step that infers alias relationships from value coincidence (e.g., "tokens that equal the old scale value get updated to the new value"). This is fragile and incorrect — multiple tokens can share the same numeric value for unrelated reasons.

**Expected output** (base=16, multiplier=1.25, Desktop + Comfortable combination):

| Token        | Pre-fix | Post-fix                 |
| ------------ | ------- | ------------------------ |
| `scale.x1`   | 20      | 20                       |
| `spacing.x1` | 16      | 20                       |
| `radius.sm`  | 16      | 16 (= scale.x0, correct) |
| `size.x3`    | 16      | 31                       |

**Scope**

This requires changes only in the resolver layer (`Resolver.resolve` or `resolveAll`). No emitter, format, or validation changes needed. The `evaluateMathExtensionsInFile` function remains correct for the single-file use case it was designed for.
