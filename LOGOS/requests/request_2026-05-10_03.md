

**Library feature request prompt:**

---

`FnTools.DesignTokens` — `evaluateMathExtensions` must propagate updated values through alias chains

**Context**

`Api.evaluateMathExtensions` was added in 0.8.0 and correctly re-evaluates `tsMathExpression` formula tokens using the active axis combination. In isolation, it works: `scale.x1` updates from stale `16` to `20` (base=16, multiplier=1.25).

**Problem**

The propagation stops there. Tokens that were resolved as aliases to `scale.x1` during `resolveAll` already have their value baked to `16` in the flat token list. `evaluateMathExtensions` does not revisit those alias results. The consumer tokens — `spacing.x1`, `radius.sm`, `size.x1`, `font-size.body`, etc. — all stay at their stale values.

Verified with this test:

```fsharp
// Before evaluateMathExtensions:
//   scale.x1   = ResolvedNumber 16.0
//   spacing.x1 = ResolvedNumber 16.0   (DimensionType — alias resolved to 16)

let result = Api.evaluateMathExtensions tokens

// After:
//   scale.x1   = ResolvedNumber 20.0   ✓ correct
//   spacing.x1 = ResolvedNumber 16.0   ✗ unchanged — alias was already baked
```

No warnings are emitted. The function silently leaves alias tokens stale.

**Root cause**

`resolveAll` + `flattenResolved` follows alias references and bakes their values as concrete `ResolvedNumber`s before `evaluateMathExtensions` runs. By the time the flat token list is produced, the information "this token was an alias to `scale.x1`" is gone from the value — only the `ResolvedNumber 16.0` remains.

**What the fix requires**

After updating a formula token's value (e.g., `scale.x1: 16 → 20`), `evaluateMathExtensions` must do a second pass over all tokens in the flat list and update any token whose pre-evaluation value exactly matched the formula token's pre-evaluation value AND which shares the same type context. More precisely: the function needs to retain the alias graph from `resolveAll` (or reconstruct it from extensions), then push updated values forward through it.

The simplest correct approach: integrate expression evaluation into `resolveAll` itself, before alias references are followed, so dependent tokens always see the evaluated value during their own resolution. This avoids the propagation problem entirely. `evaluateMathExtensions` would then become a post-processing refinement, or the functionality could move into the resolver pass directly (ADR-034 extension).

**Alternative accepted approach**

If in-resolver evaluation is out of scope: `evaluateMathExtensions` should accept a second argument — the pre-evaluation value map — and perform a propagation pass. Any token whose value equals a pre-eval formula token value and whose metadata/type is consistent should be updated to the post-eval value.

**Why `importWithResolverEvaluatingExtensions` cannot substitute**

That function runs full validation, which currently hard-fails on dimension tokens aliasing number tokens (a known structural pattern in this SoT, tolerated by the Primitives path). It is not a drop-in replacement for the Primitives workflow.

**Concrete expected output** (base=16, multiplier=1.25, Desktop combination):

| Token            | Current (broken) | Expected                                          |
| ---------------- | ---------------- | ------------------------------------------------- |
| `scale.x1`       | 20               | 20                                                |
| `spacing.x1`     | 16               | 20                                                |
| `radius.sm`      | 16               | 16 (= scale.x0, correct)                          |
| `size.x3`        | 16               | 31                                                |
| `font-size.body` | 16               | 16 (= scale.x0, correct — body font is base size) |
