`FnTools.DesignTokens` — implement `tsMathExpression` evaluation in `resolveAll`

**Context**

The library stores a custom extension on tokens:

```
"scale": {  "x3": {    "$type": "number",    "$value": 16,    "$extensions": {      "com.fntools.designtokens": {        "tsMathExpression": "round({base} * pow({multiplier}, 3))"      }    }  }}
```

`resolveAll` currently reads `$value` directly and ignores `tsMathExpression`. `$value` is a stale pre-baked integer (written by Tokens Studio at the time of the last manual save). By emit time it bears no relation to the actual formula result under the active axis combination.

**Problem**

We have a resolver document (`laura.resolver.json`) with axis sets. `Foundations/Base` defines `multiplier = 1` and scale tokens with `$value: 16`. `Breakpoints/Desktop` overrides `multiplier = 1.25`. When resolving with Desktop active, `scale.x3` should be `round(16 × 1.25³) = 31`. Instead it resolves to `16` because `resolveAll` reads the stale `$value`.

The only workaround is a preprocessing script that evaluates the formulas and writes correct `$value` fields back into the SoT — for every axis combination — before `resolveAll` runs. This is fragile and duplicates resolution logic.

**Requested change**

In `resolveAll`, after resolving all token references in a set combination, check each resolved token for `$extensions["com.fntools.designtokens"]["tsMathExpression"]`. If present:

1. Parse the expression. Variable syntax is `{tokenName}` where `tokenName` is a dot-path referring to another token resolvable in the current combined context.
2. Resolve each `{variable}` to its resolved numeric value from the current combined context.
3. Evaluate the math. Supported functions at minimum: `pow(base, exp)`, `round(x)`, `floor(x)`, `ceil(x)`, standard arithmetic operators.
4. Use the evaluated result as the token's resolved value, overriding `$value`.

If evaluation fails (variable not found, parse error, non-numeric result), fall back to `$value` and emit a warning — do not fail the whole resolution.

**Why the library rather than a script**

The expression variables reference tokens whose values are themselves axis-dependent. `{multiplier}` is `1` in `Foundations/Base` but `1.25` in `Breakpoints/Desktop`. Correct evaluation requires the combined resolved context, which only `resolveAll` has. A preprocessing script cannot replicate this without reimplementing the entire resolution pass.

**Expected outcome**

Given `base = 16`, `multiplier = 1.25` (from active axis):

| Token      | `$value` (stale) | Evaluated result |
| ---------- | ---------------- | ---------------- |
| `scale.x0` | 16               | 16               |
| `scale.x1` | 16               | 20               |
| `scale.x2` | 16               | 25               |
| `scale.x3` | 16               | 31               |
| `scale.x4` | 16               | 39               |
| `scale.x5` | 16               | 49               |

Switching axis to Tablet (`multiplier = 1.125`) should produce different values automatically without any SoT modification.

**Scope boundary**

This is purely a resolver change. No emitter changes are needed. The `emitCalcPreserving` pattern-match against `base × multiplierⁿ` will then work correctly for tokens where `round()` is absent from the formula; the `round()` interaction with `emitCalcPreserving` is a separate known limitation (ADR-027 / findings doc).
